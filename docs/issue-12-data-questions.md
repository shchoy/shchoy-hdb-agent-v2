# Issue #12: Data questions over PLG Records

Issue: https://github.com/shchoy/shchoy-hdb-agent-v2/issues/12 (child of #1; built on #4 ontology/glossary and #6 policy Q&A).

## What was built

A PLG officer can ask a numeric question in plain English and get plan → SQL → result → explanation. A new `data` agent plans, writes one read-only SQL query over PLG Records, runs it through a validator, and explains the result in terms of the glossary definition in force on the reporting date.

- **Warehouse:** DuckDB attaches `poc-data/plg_records.db` (SQLite) read-only. The connection is then locked (no external file/network access).
- **Validator:** one SELECT only, parsed by DuckDB; rejects writes, PRAGMA/COPY/ATTACH, several statements, table functions, other catalogs and the `staff` table. Then an `EXPLAIN` dry run before execution. Rejections go back to the agent with the reason.
- **Semantic layer** (`ontology/semantic.yaml`): SQL bindings keyed by versioned glossary term (`plg:Vacant_v1`, `plg:Vacant_v2`, `plg:Arrears_v1`, ...) with `$as_of` (default 2026-09-30), table notes, example queries and known data-quality issues. `make ontology` checks every binding names a glossary term and dry-runs it, then writes `generated/semantic_layer.json`.
- **Historical definitions:** `get_definition(concept, as_of | version)` returns the glossary version in force on a date with its SQL binding. At 2026-08-31, Vacant v2 gives 47 and the superseded v1 (units under tender count as vacant) gives 52, which explains the QBR/monthly-report difference.
- **`sql_trace` events:** one per query, with plan, SQL, `as_of`, status (ok/rejected), error, result summary, glossary term versions used, data-quality warnings and, on the last trace, the explanation. The explanation always names the definition versions and effective dates (appended if the agent omits them).
- **Data-quality warnings:** duplicate tenant T-10514/T-19807, duplicate payment PAY-00001235, impossible date INSP-2025-0125, outlier rent TA-2022-00400. They fire when the query reads the table and names an affected value (in the SQL or result) or matches a pattern.
- **Ground truth:** the arrears binding reproduces `_master/arrears.json` for all 135 tenancies; Golden Leaf Minimart (TA-2024-00542) is S$22,672.00, 121 days, 4.0 months of rent.
- **Graph:** the router can send a question to `knowledge`, `data` or both. A data finding with no successful query is not a sourced answer (fixed "not covered" reply).
- **Web:** `sql_trace` is in the OpenAPI schema and the zod parser. The Ask screen does not display it yet.

## Known limits

- The first query downloads DuckDB's `sqlite` extension (needs network once).
- Unit status is a snapshot at 2026-09-30; historical vacancy comes from `vacant_since`, so units vacant then but let since are not visible.
- Data-quality warnings are heuristic (named values and patterns), so some affected queries (e.g. `ORDER BY inspection_date DESC` with no row shown) are not flagged.
- Versioned term IDs are accepted at any `as_of`, so the agent can cite a superseded definition (needed for the 47 vs 52 comparison).
- The Ask screen does not render `sql_trace` yet.
